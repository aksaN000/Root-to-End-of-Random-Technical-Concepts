The 60-second versionread this first, or come back to it after the deep dive
  1. The browser draws only the DOM. Changing a variable changes nothing on screen. In plain JavaScript our script runs once, so a variable keeps its value, and we update the DOM by hand.
  2. React calls our component function again on every render, so local variables start fresh each time. useState keeps a value in a slot React owns, and setX asks React to render again and change the DOM for us.
  3. useEffect(fn, deps) is called during render, but fn is only stored. React calls it after the commit, and again only when an item in deps changed by Object.is. With [], nothing can change, so it runs once.
  4. use(promise) returns the value if the promise is done, and otherwise throws. The nearest <Suspense> shows its fallback, and when the promise settles React renders the component again. So the promise must be the same object every time: create it once, outside the component.

Frame 0 · the root

A variable never moves a pixel

The browser draws the DOM, the tree of element objects it built from our HTML (the HTML to pixels page follows that tree to the screen). Our JavaScript variables live somewhere else entirely, in the engine's memory. Nothing connects them: count++ changes a number in memory, and the screen stays exactly as it was until some code writes to the DOM.

In plain JavaScript that code is ours. The script runs once, top to bottom, so a variable declared at the top keeps its value for the life of the page. A click handler runs again on every click, changes the variable, and then must also change the DOM element that shows it.

What it is. Two counters. The left one is real plain JavaScript running on this page. The right one is a small imitation of React's cycle: a function that returns what the screen should show, called again after every change.

So plain JavaScript has no "re-render" at all, and no need for useState. Its variables never reset, because nothing calls the script again; and the screen changes only where we write to the DOM. Forget one write (tick the box above) and the screen is silently wrong. React exists to remove step 3 from our code: we change data, and React works out every DOM change.

Frame 1 · React calls our function again

useState: a slot that survives the next call

A React component is a function, and React calls it whenever it needs to know what the screen should look like. That call is a render. Changing the real DOM to match is the commit. Each render is a fresh function call, so let count = 0 inside the component is created again, set to 0, every time.

So the value has to live outside our function. React keeps one object per component instance, a fiber, and on it a list of hooks in call order. The first time useState runs, mountStateImpl makes a hook, stores our starting value in hook.memoizedState, and mountState returns it with a dispatch function bound to this fiber. That pair is the [count, setCount] we destructure. On later renders useState ignores the starting value and returns what the slot holds.

Calling setCount runs dispatchSetStateInternal. Usually it queues the update and calls scheduleUpdateOnFiber: that is the request to render again. But first it may try a shortcut. If nothing else is pending on this fiber or its alternate (the copy from the previous render), it computes the new state right away and compares it with Object.is. Equal means there is nothing to do, and React returns without scheduling a render.

The shortcut has a condition, and real React shows it. Right after a real update, the old fiber still carries that update's lane, so the check at the top fails. The first setCount(sameValue) then does call our component once; React finds every state unchanged and throws that render away, with no commit and no effect. The next same-value call takes the shortcut. The dependency-array lab reproduces this exactly (try "count + 1", then "same value" twice), and the react.dev page warns that React "may still need to call your component before skipping the children".

Frame 2 · effects

useEffect is called now; our function runs after the commit

The line useEffect(() => { … }, []) holds two functions. useEffect itself is called during the render: the brackets after its name call it. Our arrow function is only passed to it as a value, like the function we pass to setTimeout(fn, 1000) or button.addEventListener("click", fn). Those calls run now and keep fn for later; useEffect does the same.

On the first render, mountEffectImpl receives our arrow as create and pushes it onto the fiber's effect list, flagged HookHasEffect ("run me"). There is no create() anywhere in it. After the commit has changed the DOM, commitHookEffectListMount walks that list and, for every effect with the flag, finally calls create(). That is the moment our fetch starts. Waiting until then means the page (here, the spinner) is already on screen, and React can check the dependency array on later renders before deciding whether to run the effect at all.

Frame 3 · the dependency array
What goes in [ ], and when the effect runs again

  

    
On every render after the first, updateEffectImpl runs instead. If we passed an array, it hands this render's array and the previous one to areHookInputsEqual, which walks them item by item with is, React's name for Object.is. All equal: the effect is pushed without HookHasEffect, and the commit skips it. Anything different, or no array at all (nextDeps is null, so the comparison is never made): the flag is set and the effect runs after the commit.

    
So the array holds the values our effect reads: state, props, or anything computed from them. React's rule is that every such value belongs in it. Our fetch reads nothing that can change (a fixed file name), so [] is correct, and with an empty array the loop has nothing to compare and always answers "equal".

Frame 4 · use() and Suspense
A component that throws, and a boundary that catches

  

    
use, added in React 19, reads a value from a promise during render. It first checks that it was given a "thenable" (an object with a .then method), then trackUsedThenable looks at a property React writes onto the promise itself: status. If it says "fulfilled", use returns value straight away. If the promise has no status yet, React sets it to "pending", attaches its own .then that will write status and value when the promise settles, and then throws SuspenseException. Our component stops on that line; the rest of it never runs.

    
The throw unwinds React's work loop up to the nearest <Suspense>, which renders its fallback instead, and React commits that. It also attaches a ping listener to the same promise. When the promise settles, pingSuspendedRoot marks the root and schedules a render. React then calls our component again from the top; this time status is "fulfilled", so use returns the data.

  

  

    
    
  

  
  

    
Because React re-runs the component rather than resuming it, the promise must be the same object on the retry: only that object carries status: "fulfilled". In our file it is created once, at the top level, when the module first runs. If we wrote use(loadTechnologies()) inside the component, each retry would make a brand-new promise with no status, start another request, and suspend again, forever. Real React does exactly that: 22 requests in two seconds and the spinner never leaves (Real output). React's development warning "A component was suspended by an uncached promise" fires only when it re-runs the same render attempt and sees a different promise at the same position; in this loop each attempt is new, so we saw no warning at all.

    
One step real React takes that our first sketch missed: right after committing the fallback, React 19 renders the suspended part once more, while the promise is still pending, to warm up siblings it skipped during the unwind. use throws again and nothing on screen changes. The lab shows it as its own step, because real React logs it.

Why async goes on a helper, never on the component or the effect. An async function always returns a promise. A component in the browser must return JSX, not a promise (React 19 throws "async Client Component" when it detects one), and an effect function may return only nothing or a cleanup function. So both versions put async on loadTechnologies and call it.

    
The blank page we hit while writing this. The file was public/Technologies.json, and the code fetched /technologies.json. Windows file names ignore case; URLs do not, and neither does Vite's list of public files or a Linux server like Netlify's. The server answered with a 404 page, res.json() failed on its first character ("Unexpected token '<', "<!doctype "... is not valid JSON"), the promise rejected, use threw that error, and with no error boundary to catch it React removed the whole tree. Real React does exactly this in our check. The name in fetch must match the file name exactly.

  

  
Which to submit: the use() + Suspense version. It has less code, fetches once even in development, and needs no loading state of our own. The useEffect version is the one most tutorials and existing projects use, so it is worth recognising, and react.dev points out its weak spots (race conditions, no caching) in "You Might Not Need an Effect".

          A student writes fetch("/Technologies.json").then(r => r.json()).then(d => setTechnologies(d)) directly in the component body. The Network tab shows the request repeating forever. Explain why, naming the comparison React uses, and give two correct fixes.
          
      
          
        
          The component body runs on every render. Each response calls setTechnologies with a new array from JSON.parse; Object.is(oldArray, newArray) is false because they are different objects, so React schedules another render, which runs the fetch again: a loop.
          
        
          Fix 1: move the fetch into useEffect(…, []), which React runs once after the first commit. Fix 2: create the promise once at module level and read it with use(promise) inside a component wrapped in <Suspense>.
          
        
          Marking: 1 for "body runs every render", 1 for the new array, 1 for Object.is, 1 per fix.

          Compare use(promise) with Suspense and useEffect with useState for loading data once: when the request starts, where the data lives, what triggers the second render, and how many requests the development build sends under StrictMode.
          
      
          
        
          use + Suspense: the request starts when the module runs (before any render); the data lives on the promise as status/value; React's ping listener on the promise schedules the retry; 1 request in development. useEffect + useState: the request starts after the first commit; the data lives in state slots on the fiber; our setTechnologies/setLoading schedule the render; 2 requests in development because StrictMode runs effects twice (1 in production).

          Write a short note on why the promise given to use() must be created outside the component that reads it.
          
      
          
        
          When use meets a pending promise, React tags it status: "pending", attaches listeners that will write status and value, and throws to the nearest Suspense. When the promise settles, React renders the component again from the top; it does not resume it. Only the original promise object carries "fulfilled", so the retry must receive the same object. A promise created inside the component is new on every render, has no status, starts a new request, and suspends again forever (22 requests in 2 s in our capture). Creating it once at module level, or in a cache or a framework, gives every render the same object.
          
        
          Marking: 1 for the status written on the object, 1 for "re-run, not resume", 1 for the infinite loop, 1 for where to create it.
