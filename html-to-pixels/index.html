From HTML bytes to pixels

The previous page ended with bytes arriving through a data pipe. When those bytes are an HTML document, they go into Blink's HTML parser, become a DOM tree, and then pass through style, layout, paint and compositing before anything reaches the screen. We step through the parser on any HTML we type, check every tree against this browser's own parser, and then read real Chrome traces that show exactly which stages a DOM change triggers.

The 60-second versionread this first, or come back to it after the deep dive
  1. The tokenizer is a state machine that reads characters and emits tokens: start tags, end tags, text, comments. For our 450-byte test page, Chrome's trace says it produced exactly 46 tokens, and so does our model.
  2. The tree builder turns tokens into the DOM using a stack of open elements and an insertion mode. It repairs broken HTML with fixed rules (implied tags, <p> auto-closing, the adoption agency), which is why every browser builds the same tree from the same mess.
  3. Then the rendering lifecycle runs: style → layout → pre-paint → paint → commit, then raster and draw on other threads. A change only reruns the stages after it: color repaints, width re-lays out, and transform on its own layer skips both.
  4. Layout is lazy, until we ask. Reading offsetHeight right after a write forces layout now. In a real trace, 20 write-then-read pairs ran layout 20 times; the same writes followed by one read ran it once.
The parser lab builds a DOM from anything we type and checks it against this browser. The cost lab replays real traces for seven changes, including the forced-layout loop.
Frame 0 · the tokenizer

Bytes become characters, and characters become tokens

The bytes are first decoded to characters (our page declared UTF-8). Then HTMLDocumentParser::PumpTokenizer runs a loop: ask the tokenizer for the next token, hand it to the tree builder, repeat. The loop has a budget. After a number of tokens or a time limit it yields, returning to the event loop so the page can render what it has so far. That is how a long page shows content before the parser reaches the end.

The tokenizer itself is the state machine from the HTML standard, written as a big switch. In the data state, < moves to the tag-open state; a letter there begins a start tag; / begins an end tag; ! leads to comments and DOCTYPEs; anything else means the < was just text.

Chrome's trace of our test page recorded one ParseHTML event with parsed_bytes: 450 and parsed_tokens: 46. Our model's tokenizer, given the same 450 bytes, emits 46 tokens before end-of-file. Text between two tags is buffered into a single character token, which is why the counts line up.

    Frame 1 · the tree builder
    Tokens become a DOM, and broken HTML is repaired the same way everywhere
    
  
    
    
    The tree builder is a second state machine. Its state is the insertion mode (initial, before html, in head, in body and more), and it keeps the stack of open elements, whose top is where new nodes go. Most rules are about missing or misplaced tags. A block element such as <div> first closes any open <p>; a new <li> closes the previous one; text with no <html>, <head> or <body> gets all three implied.
    
    
    Formatting elements such as <b> and <i> also live on a second list, the active formatting elements. When they are closed in the wrong order, the adoption agency algorithm moves nodes around so the result is still a tree. When text appears after a block closed them, they are reconstructed (reopened). Try "Misnested b and i" and "b around a p" in the lab.
    
  
    
  
    
    
    
  
    
  
    Each element the tree builder creates is a C++ object (HTMLParagraphElement, HTMLDivElement, …) on Blink's garbage-collected heap. JavaScript never touches it directly. document.querySelector returns a V8 wrapper object, and its properties call generated binding code; that is why the method for offsetHeight below is named offsetHeightForBinding.
    

    


    
  
    Frame 2 · the rendering lifecycle
    Style, layout, pre-paint, paint: one ordered pipeline
    
  
    
    
    A DOM is not pixels. Blink runs each document through a fixed lifecycle, enforced by a state machine in document_lifecycle.h. Style computes each element's final CSS values. Layout computes boxes: positions and sizes. Pre-paint builds property trees (transforms, clips, effects). Paint records display lists, meaning drawing commands rather than pixels. Commit hands the result to the compositor thread, worker threads raster it into pixels, and the GPU process draws the frame.
    
    
    Changing the DOM or a style does not run these stages at once. It marks things dirty and calls ScheduleLayoutTreeUpdate, which asks for a visual update. The stages run later, in the next frame's BeginMainFrame, and only from the first dirty stage onward.

    Frame 3 · forced synchronous layout
    Why reading offsetHeight after a write runs layout right now
    
  
    
    
    A layout read such as offsetHeight has to return a correct number, so it cannot wait for the next frame. The binding calls UpdateStyleAndLayoutForNode, which runs style and layout immediately, inside our script. One read is fine. But a loop that alternates writing a style and reading a layout value forces a full style-and-layout pass on every iteration. This is layout thrashing.

    Frame 4 · paint and composite
    Layers, raster on worker threads, and why transform is cheap
    
  
    
    
    Paint does not produce pixels. It records drawing commands into display lists, grouped by layer. In our load trace there are two Paint events: one for the document and one for DIV id='mover', because will-change: transform gave that element its own composited layer.
    
    
    After Commit, the compositor thread owns a copy of the layer tree. RasterTask events run on ThreadPoolForegroundWorker threads, turning display lists into pixel tiles, and the frame is drawn. A transform on a layer that already exists changes only how the compositor places that layer. In the trace that change produced no Layout, no Paint and no RasterTask: the same pixels, moved.
    
  
    
  
    This is also why the main thread matters so much. Everything before commit (our JavaScript, style, layout and paint) runs on CrRendererMain, one task at a time, as the event-loop page showed. A long task delays the next frame's lifecycle. Compositor-only changes, such as scrolling or a transform on an existing layer, can keep moving while the main thread is busy.

    Exam practice
    Exam-style questions, with model answers
    
  
    Five questions in the style of a web systems or browser internals exam. Write our answer on paper first, then open the model answer and mark ourselves honestly. The marks follow the usual pattern of university theory exams; they are not copied from any real paper.
    
  
    
    
    Self-marks stay on this page only; refreshing clears them.
    
    
    
      
    Give the DOM tree, in html5lib format, for <p>One<b>two<p>three</b>four, and name the rule responsible for each surprising part.
    
      
    
        
    | <html>
|   <head>
|   <body>
|     <p>
|       "One"
|       <b>
|         "two"
|     <p>
|       <b>
|         "three"
|       "four"
    
        
    Implied tags: no DOCTYPE, html, head or body, so all are created. The second <p> closes the first, because a <p> start tag closes an open p in button scope; that pops the b too. Reconstruction: b is still in the active formatting list, so when "three" arrives it is reopened inside the second p. </b> runs the adoption agency; b is the current node with no block inside it, so it is simply popped, and "four" goes into the p. (Produced by our model and identical to Chrome's parse.)
    
        
    Marking: 2 for the tree, 1 each for implied tags, the p closing, reconstruction, and the end of b.
    
      
    
    
    
    
    
      
    Trace the adoption agency algorithm for <b>1<p>2</b>3</p>. What are the formatting element and the furthest block, and what is the final tree?
    
      
    
        
    When </b> arrives, the stack is html, body, b, p and the active formatting list holds b. The formatting element is that b. The furthest block is the topmost special element above it on the stack: the p. The common ancestor is body.
    
        
    The algorithm moves the p out of b and appends it to body, creates a new b, moves p's children ("2") into the new b, and appends the new b to p. The old b is removed from both lists, and the new b is put on the stack after p. On the second outer iteration the new b has no block above it, so it is popped. "3" then goes into p.
    
        
    | <html>
|   <head>
|   <body>
|     <b>
|       "1"
|     <p>
|       <b>
|         "2"
|       "3"
    
        
    Marking: 1 for the formatting element, 1 for the furthest block, 2 for the restructuring steps, 1 for the final tree.
    
      
    
    
    
    
    
      
    Using the rendering lifecycle, explain why changing color does not trigger layout, why changing width does, and what a transform on an element with will-change: transform skips. Cite trace evidence.
    
      
    
        
    Every change invalidates from the earliest stage whose output it affects. color changes computed style and the drawing commands, but no box sizes or positions: the trace shows UpdateLayoutTree and Paint but no Layout. width changes box geometry, so layout is dirty and everything after it reruns: one Layout event with dirtyObjects: 4 of 23. A transform on an element that already has its own composited layer changes only a node in the transform property tree; the compositor re-positions the existing layer. The trace shows no Layout, no Paint and no RasterTask, only PrePaint, Layerize and Commit.
    
        
    Marking: 1 per property with the right stage, 1 for citing the trace counts.
    
      
    
    
    
    
    
      
    The layout is clean when this runs. for (let i = 0; i < 100; i++) { const w = items[i].offsetWidth; items[i].style.width = (w + 10) + "px"; } How many forced layouts happen inside the loop? Rewrite it to need none, and say when layout then runs.
    
      
    
        
    99 forced layouts. The first read finds layout clean and needs no work. Every later read comes after a write in the previous iteration, so each of the remaining 99 reads runs UpdateStyleAndLayout. A final layout also runs in the next frame.
    
        
    const widths = items.map(el => el.offsetWidth);              // reads: layout is clean
items.forEach((el, i) => { el.style.width = (widths[i] + 10) + "px"; }); // writes only
    
        
    Now no read follows a write, so nothing is forced inside the script. Style and layout run once, in the next frame's lifecycle update.
    
        
    Marking: 2 for 99 with the reason, 2 for a read-all-then-write-all rewrite, 1 for "one layout at the next frame".
    
      
    
    
    
    
    
      
    List the tokenizer states, in order, that the HTML standard's tokenizer passes through for <a href="x">, starting in the data state, and say what is emitted.
    
      
    
        
    Data → (<) tag open → (a) tag name → (space) before attribute name → (h) attribute name → (=) before attribute value → (") attribute value (double-quoted) → (") after attribute value (quoted) → (>) emit the start tag token and go back to the data state.
    
        
    One token is emitted: a start tag named a with one attribute, href="x", not self-closing. In Blink these are the kTagOpenState, kTagNameState and attribute states of HTMLTokenizer::NextTokenImpl.
    
        
    Marking: 3 for the states in order, 1 for the emitted token.
