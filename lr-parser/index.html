Shift, reduce, accept: building an LR parser from a grammar

The V8 page shows a hand-written parser. Most language tools instead generate their parser from a grammar: Bison, yacc, and the parsers inside PostgreSQL, Bash and GCC's old C front end. This page builds an SLR parser in front of us from any grammar we type: FIRST and FOLLOW sets, LR(0) item sets, the parsing table, and a step-by-step parse that grows its tree. Then we open real Bison and see the same machine in C.

The 60-second versionread this first, or come back to it after the deep dive
  1. An LR parser reads tokens left to right, shifting them onto a stack until the top matches a rule's right-hand side, then reducing it to the rule's left-hand side.
  2. When to reduce is precomputed: LR(0) item sets form an automaton, and a table maps (state, next token) to shift, reduce, accept or error.
  3. SLR places reduce actions on the FOLLOW set of the rule's left side. Bison's LALR(1) uses sharper per-state lookaheads, so it accepts more grammars.
  4. A cell with two actions is a conflict. The dangling else is the classic one; Bison resolves it by shifting.

Frame 0 · the idea

Why parse bottom-up

A top-down parser, like V8's, guesses which rule to use from the next token and calls a function per rule. An LR parser waits: it shifts tokens onto a stack until the top of the stack matches the right-hand side of a rule, then reduces it to the rule's left-hand side. It finishes when the whole input has been reduced to the start symbol. Read backwards, the sequence of reductions is a rightmost derivation.

The hard part is knowing when to reduce. The answer is a finite automaton over "items", compiled into a table of ACTION and GOTO entries. That compilation is what a parser generator does, and it is what we watch below.

Grammar lab · drives every frame below

One rule per line: A -> x y | z. Symbols are separated by spaces. Anything never on a left-hand side is a terminal. Use ε for an empty alternative. The first rule's left side is the start symbol.

Frame 1 · analysis

Augment the grammar, then compute FIRST and FOLLOW

We add a new start rule S' → S so that "reduce to S'" can only mean "accept". FIRST(X) is the set of terminals that can begin a string derived from X. FOLLOW(A) is the set of terminals that can appear immediately after A in some sentential form. SLR uses FOLLOW to decide where to place reduce actions.

Frame 2 · the automaton

LR(0) items, CLOSURE and GOTO

An item is a rule with a dot showing how much of it we have seen: E → E · + T means "we have an E and expect + T next". A state is a set of items. CLOSURE adds, for every nonterminal right after a dot, all of its rules with the dot at the start. GOTO(I, X) moves the dot over X in every item of I that allows it, then takes the closure. Starting from CLOSURE({S' → · S}) and applying GOTO until no new state appears gives the canonical collection.

Bold items are the kernel; the rest came from CLOSURE. Purple items have the dot at the end, which means a reduction is possible. Click a transition to see its target state.

Frame 3 · the table

The SLR parsing table

The rules are short. For an item A → α · a β with terminal a, ACTION[i, a] = shift to GOTO(i, a). For a complete item A → α ·, ACTION[i, b] = reduce by that rule for every b in FOLLOW(A). For S' → S ·, ACTION[i, $] = accept. GOTO entries come straight from the automaton. If any cell gets two actions, the grammar is not SLR(1), and the cell turns red.

sn = shift and go to state n · rn = reduce by rule n · acc = accept · blank = syntax error · right of the bar: GOTO

Frame 5 · the real thing

Inside a Bison-generated parser

We gave Bison the expression grammar and compiled the result with GCC. Bison builds LALR(1) tables rather than SLR. For this grammar they make the same parsing decisions, but Bison numbers states differently and adds one state for shifting the end-of-file token. The driver is the C function yyparse, and it is our Step button written with labels and goto.

Compare Bison's trace with ours. Bison reduces before reading the next token ("Reducing stack by rule 6" appears before "Reading a token"). That is a default reduction: when a state's only sensible action is one reduction, yypact says so and yydefault skips the lookahead. Our SLR driver always reads the lookahead first. The tables are also compressed into yypact, yytable and yycheck instead of a full two-dimensional array.

Frame 6 · when it breaks

Conflicts: the dangling else, and where SLR is too weak

The dangling else. In if c1 then if c2 then s1 else s2, which if owns the else? The grammar allows both, so there is a state where the parser could either shift else or reduce the inner if. Load the "Dangling else" preset in the lab and find the red cell. Bison reports the same conflict and shows both derivations; by default it shifts, attaching else to the nearest if. Declaring precedence silences it.

SLR is not always enough. The classic Dragon Book grammar for C-style assignments (S → L = R | R, L → * R | id, R → L) is unambiguous, yet SLR gets a shift/reduce conflict on =: = is in FOLLOW(R), because of *R = …, even in the state where reducing L to R can never be followed by =. Load the "SLR fails" preset to see it. LALR computes lookaheads per state instead of per nonterminal, so Bison builds this grammar without any conflict.

For S → A a | b A c | d c | b d a and A → d, compute FIRST and FOLLOW of S and A, and show that the grammar is not SLR(1).

FIRST(S) = { b, d }, FIRST(A) = { d }. FOLLOW(S) = { $ }, FOLLOW(A) = { a, c }.

The state reached on d from I0 contains S → d · c and A → d ·. SLR puts "reduce A → d" on every token in FOLLOW(A), including c, which collides with the shift on c. Likewise, after b d the state holds S → b d · a and A → d ·, with a conflict on a. So there are two shift/reduce conflicts.

The grammar is still LALR(1): in the first state the only valid lookahead for A → d · is a, and in the second it is c, so per-state lookaheads separate the actions.

Marking: 2 for the sets, 2 for locating and explaining a conflict.

Explain the shift/reduce conflict in S → if E then S | if E then S else S | other. How does yacc/Bison resolve it by default, and how can the grammar author state the choice explicitly?

After if E then if E then S, with else as the next token, the parser can either reduce the inner if E then S (so the else belongs to the outer if) or shift else (so it belongs to the inner one). Both choices give a valid parse, so the grammar is ambiguous and the table cell has two actions.

Bison reports "1 shift/reduce conflict" and resolves it by shifting, which matches each else with the nearest unmatched if, the rule in C and Java. To say this explicitly, declare %nonassoc THEN and then %nonassoc ELSE: ELSE gets higher precedence than the rule ending in THEN, so the conflict is resolved as a shift without a warning. The alternative is rewriting the grammar with matched and unmatched statements.

Marking: 2 for the two derivations, 1 for the default, 1 for a precedence fix.

Why does S → L = R | R, L → * R | id, R → L have an SLR conflict, even though it is unambiguous? Why does LALR(1) not have it?

In the state reached on L from the start, the items are S → L · = R and R → L ·. SLR reduces R → L on every token in FOLLOW(R). Because of S → L = R and L → * R, = is in FOLLOW(R), so the cell for = holds both "shift" and "reduce": a shift/reduce conflict.

But in this state, reducing to R can only finish a whole statement S → R, so the only valid lookahead is $. LALR(1) computes lookaheads per state, so it reduces only on $. Bison builds this grammar without warnings; its state 4 says '=' shift and $default reduce using rule 5 (R).

Marking: 2 for locating the conflict via FOLLOW(R), 2 for the per-state lookahead explanation.
