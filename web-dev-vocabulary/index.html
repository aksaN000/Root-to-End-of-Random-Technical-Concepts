From the engine to the plugin

Node, npm, npx, package, registry, scope, library, framework, dev server, bundler, API, callback, hook, plugin, utility class. Starting a React project means meeting all of these words at once. We put each one where it lives, from the node binary up to the Tailwind class on our button, and show the real code behind it. Two labs read commands and class names exactly the way npm and Tailwind do. The last part covers how to keep all of it in our heads: what memory research says, and a trainer that uses it. This page picks up below the V8 page and the event-loop page, which explain how the engine runs our code once it gets there.

The 60-second versionread this first, or come back to it after the deep dive
  1. JavaScript runs in two places. An engine (V8) executes the language. A runtime is an engine plus the abilities of where it runs: the browser adds the DOM, and Node adds files and the network. Our tools run in Node on our machine. Our app runs in the user's browser.
  2. A package is a folder of code with a package.json, downloaded from the registry by npm. In @tailwindcss/vite@4.3.3, the @ at the front starts a scope (the owner), and the @ after the name starts a version. We call a library; a framework calls us.
  3. Every command is program, command, arguments, options, separated by spaces. npx X is npm exec -- X, and npm create vite runs the package create-vite. A lone -- means "the rest is not for npm". npm run dev finds vite because npm puts node_modules/.bin first on PATH.
  4. Vite is a dev server and a build tool. For each file the browser asks for, it calls every plugin's transform hook, a callback it calls at a fixed moment. React's plugin compiles JSX there, and Tailwind's writes the CSS for the class names it found. A class such as px-4 is one CSS rule: padding-inline: calc(var(--spacing) * 4), which is 16px.

Frame 0 · the root

A program is a file the operating system runs

When we type node hello.js, the shell asks the operating system to start the program file node, passing the words node and hello.js as its arguments (argv). That file is ordinary compiled C++, like any program built with gcc. Its main function is three lines, and it calls node::Start.

Start does three jobs. It initializes V8, Google's JavaScript engine, the same one inside Chrome. It creates an environment with Node's own objects: process, require and the file and network modules. Then it runs our script and spins the event loop (libuv's loop), which keeps the process alive while timers, files or sockets are pending. So "Node" is a C++ program that embeds V8 and adds system abilities. It is not a compiler and not a language.

The one thing to remember: every tool on this page (npm, npx, vite, tsc) is a JavaScript program, and node is the program that runs it. When we type npm, the operating system starts node with npm's script, npm-cli.js.

Frame 1 · engines and runtimes

The same engine in two different houses

An engine executes one language: it parses the text, compiles it to bytecode, interprets it and compiles hot code to machine code (just-in-time, or JIT). The V8 page follows one expression through those steps. A runtime is an engine plus everything the place it runs in adds, such as the global objects, the APIs and an event loop. The language is the same in both, but the objects available to it differ.

We asked both runtimes the same question, typeof window, typeof document, typeof process, typeof require, and recorded what each one answered.

Frame 2 · code we didn't write

Modules, packages, the registry and scopes

A module is one file that shares things with other files through export and import. Navbar.tsx ends with export default Navbar, and App.tsx gets it back with import Navbar from './components/Navbar'. A package is a folder of modules with a package.json label, published so anyone can install it. Our own project is a package too.

The registry is the server that stores every published package, and npm's is registry.npmjs.org. It works like an app store for code: authors publish to it, and npm install downloads from it. A package name is unique across the whole registry and belongs to whoever published it first, which causes two problems. Good short names run out, and anyone can take a name that sounds official. A scope solves both. It is a prefix such as @tailwindcss/ owned by one account or organisation, and only that owner can publish under it. Scopes work like folders: @tailwindcss/vite and @sentry/vite are two different packages, both called vite.

Here is the real conversation with the registry during our npm install. Each line is one HTTP request asking the registry about a package, and the answer lists every version with its download address. The scoped name @types/node goes out as @types%2fnode: the slash is URL-encoded, so the server sees one name and not a folder path. That is the line this.escapedName = name.replace('/', '%2f') in npm-package-arg.

The two @ signs mean different things. An @ at the start begins a scope, and an @ after the name begins what we want: an exact version (4.3.3), a range (^4.3.0 means 4.3.0 or newer but below 5), or a tag (latest, a name the registry points at a version, shown above). With nothing after the name, npm uses the range *, any version, and picks the newest.

Library or framework: who is in charge

The difference is who calls whom. We call a library: our code decides when to use it, and it does one job and hands control back. toast("Added!") from react-toastify is a library call. A framework calls us. It runs the program and calls our code when it needs to, much like a form whose questions and order are already decided, where we only fill in the blanks. In Next.js we write app/about/page.tsx, export a function and never call it ourselves. Next.js creates the /about address and calls our function when someone visits. This is called inversion of control, also known as the Hollywood principle: "don't call us, we'll call you".

Where React fits: in between. We call it (createRoot(…).render(<App />)), and then it calls our components. It calls itself a library because it handles only the UI and leaves routing, data loading and building to us. Next.js makes those decisions for us, and that is what makes it a framework.

Frame 3 · commands

How npm reads a command line

Every command has the same grammar: program (which tool), command (what to do), arguments (what to do it to), and options (settings that start with a dash: one dash and a letter like -D, or two dashes and a word like --save-dev). Spaces separate the parts. The shell (bash, PowerShell) splits the line into words and starts the program; the program never sees the spaces. After that, npm runs four small steps of its own code. We follow each one.

  1. npx is npm exec. The npx program is a tiny script: it inserts exec as the first word and puts -- in front of the first word that is not an option. So npx tsc --noEmit becomes npm exec -- tsc --noEmit, and --noEmit goes to tsc, not to npm.
  2. Options are sorted out by nopt. nopt walks the words and looks each option up in npm's definitions. -D is a shorthand for --save-dev, and -gD means -g -D because every letter is a one-letter shorthand. An option npm does not know, such as --template, becomes a true/false npm setting, and the word after it is left as an ordinary argument. A lone -- stops option parsing, and everything after it is kept as it is.
  3. The first plain word becomes a command. cmd-list.js holds the 67 commands and the aliases: i is install, run is run-script, and create is init. It also accepts any unambiguous abbreviation (insta) and a few common typos (isntall).
  4. Each package argument is read by npm-package-arg into a name, a scope and a version, range or tag, as in Frame 2.

Why npm create vite@latest dev-stack -- --template react-ts needs the --. create is init, and npm init vite@latest turns the name into create-vite@latest and runs it with npm exec. The real output in Frame 6 shows this: npm prints > create-vite dev-stack --template react-ts. Without the --, nopt reads --template as an unknown npm setting (template = true), so react-ts becomes a stray argument and create-vite never sees --template. The command lab shows both versions.

Why npm run dev finds vite when typing vite in the terminal says "command not found". Every package that provides a command declares a bin, and npm links it into node_modules/.bin. Before running a script, npm's run-script library puts that folder at the front of PATH, the list of folders the operating system searches for programs. It adds node_modules/.bin for the project folder and for every folder above it. We added a script that prints the first entries of PATH and ran it.

The one thing to remember: npm run dev, npx vite and node node_modules/vite/bin/vite.js all start the same program. They differ only in how the word vite gets turned into a file. And npm always works on the package.json in the folder the terminal is in.

Frame 4 · the tools

Vite serves our files, transforming each one on request

Browsers run JavaScript, not TypeScript or JSX, and they import modules by URL, not by package name. Something has to translate. Vite does that in two ways. As a dev server (npm run dev), it serves our project on localhost and transforms each file when the browser asks for it, so starting is instant and a saved file updates in place (hot module replacement). As a build tool (npm run build), it transforms everything once, bundles the many modules into a few files and minifies them into dist/ for a host to serve.

Every request goes through loadAndTransform: load the file, then transform it, which means calling the transform function of every plugin in order. Each plugin receives the code and the file's id, and can return new code.

This is what the browser actually received when it asked our dev server for /src/App.tsx. The type annotation : Props is gone, because Vite removes types without checking them. That is the job of our editor and of tsc in npm run build. Each <nav> became a call, _jsxDEV("nav", { className: … }), that returns a plain object. And import { useState } from "react" became a real URL, /node_modules/.vite/deps/react.js, because a browser cannot look up a package name.

Frame 5 · extending tools

API, callback, hook, plugin: four words for one arrangement

Read these in order, because each one builds on the one before.

  1. API: the named functions and objects a program lets other code use, like the buttons on a remote. Examples: the DOM's document.querySelector, React's useState, Node's fs.readFile. We call it.
  2. Callback: a function we hand to other code so that it can call it at the right moment, as in addEventListener('click', fn), onClick={…} or the function given to .map(…). It calls us. A common mistake is addEventListener('click', sayHi()): the parentheses call sayHi immediately and hand over its result instead of the function.
  3. Hook (in tools): a named moment in a host's work where it calls the callbacks plugins gave it. Vite's include config (reading settings), transform (each file) and buildEnd. The loop in Frame 4 is the transform hook being called.
  4. Plugin: a package of callbacks for a host's hooks, which adds a feature without changing the host's code. A Vite plugin is an object with a name and hook functions. react() and tailwindcss() in vite.config.ts return such objects. A plugin can be a host too: Tailwind is a plugin of Vite, and daisyUI is a plugin of Tailwind.

Frame 6 · Tailwind

A class name is a small CSS rule, written only if we use it

Tailwind CSS is a list of ready-made utility classes, each one a small CSS rule. Its Vite plugin reads our files, collects every word that looks like a class name, and writes CSS for exactly those words. utilities.ts registers every family. Here is the padding family, which maps px to padding-inline. The spacing helper turns the number into --spacing(4), and that becomes calc(var(--spacing) * 4). The theme sets --spacing: 0.25rem, so px-4 is 1rem, which is 16px. The multiplier must be a multiple of 0.25, so p-2.5 works and p-0.3 produces nothing.

A variant is a prefix ending in a colon that wraps the rule in a condition. lg: wraps it in @media (width >= 64rem), so it applies from 1024px wide and up, and a class with no prefix applies at every width. This is what "mobile-first" means: we write the phone layout plainly, then change it for bigger screens. hover: holds a detail many tables leave out. It adds :hover and also wraps the rule in @media (hover: hover), so a phone, which cannot hover, does not keep the colour after a tap. Variants stack from left to right: lg:hover:x puts the lg media query on the outside.

Here is the real stylesheet the dev server sent for our navbar. Every class we used has exactly one rule, and nothing else is there, except a few extra words that happen to be class names somewhere in the project's files (transform, filter). Tailwind's scanner reads every file that git does not ignore, so a word in a README can produce CSS too. That is harmless, and it shows that the scanner matches words, not meaning. Our own bg-brand appears because of the @utility rule in index.css, which is how it works with hover: and lg: like a built-in class.

Frame 7 · our code

The whole trip in our dev-stack project

Now every word together, in the order things happen when we work on the assignment. Steps 1 to 4 and 7 to 9 run in Node on our machine; steps 5 and 6 run in the browser.

  1. npm create vite@latest dev-stack -- --template react-ts: create is init, which runs the package create-vite. It writes the project folder and its package.json (real output below).
  2. npm install: Node runs npm, which asks the registry about every dependency (135 requests in our capture) and unpacks them into node_modules, recording exact versions in package-lock.json.
  3. npm install tailwindcss @tailwindcss/vite daisyui and two lines in vite.config.ts and index.css: Tailwind becomes a Vite plugin, and daisyUI a Tailwind plugin.
  4. npm run dev: npm reads "dev": "vite", puts node_modules/.bin on PATH, and Node starts Vite's dev server on localhost:5173 with the react() and tailwindcss() plugins loaded.
  5. The browser asks for index.html, then /src/main.tsx, and Vite transforms each file as it is requested: types removed, JSX turned into calls, imports rewritten to URLs, CSS written for the classes used.
  6. The browser runs it: V8 runs React, React calls our components and builds DOM nodes, and Blink does style, layout and paint (HTML to pixels). A click finds its way back to our onClick (a click to our listener).
  7. Type checking, alongside: the editor runs TypeScript and underlines errors in red. Vite ignores types.
  8. npm run build: tsc -b stops on any type error, then Vite bundles and minifies into dist/ (the real output is in Frame 4).
  9. Deploy: Netlify or Vercel serves dist/. From then on, only users' browsers run our code.
Remembering it

How to keep all of this in our heads

This page holds about a hundred words, twenty commands and the five Tailwind rules. Reading it again tomorrow will feel productive, and it is one of the least effective things we can do. This is one of the best-replicated findings in learning research. A 2013 review of ten study techniques by Dunlosky and colleagues rated practice testing (recalling from memory) and distributed practice (spacing reviews out) as the two most useful. It rated rereading and highlighting low, because they make material feel familiar without making it retrievable. Below is what each technique is, why it works, and exactly how to apply it to this page.

1 · We forget fast, then slower: the forgetting curve

Ebbinghaus measured his own memory for nonsense syllables in 1885, and Murre and Dros repeated the experiment in 2015. Most of what we learn is lost within the first day, and what survives fades more slowly after that. The useful part is that each successful recall makes the next drop slower. The chart below illustrates the shape. It is not a measurement of us: retention decays as e−t/S, and each review multiplies the stability S by 2.5. Add reviews and watch the curve flatten.

What it is. A drawing of the textbook model: exponential decay whose time constant grows after each successful review.

Checked against. Nothing numerically. The shape (steep at first, flatter after each spaced review) is what Ebbinghaus, Murre and Dros, and the spacing literature report.

Not covered. Real retention depends on the material, sleep, and how hard each recall was. Use the shape, not the numbers.

2 · Recall, don't reread (retrieval practice)

Roediger and Karpicke had students either reread a passage or try to write down what they remembered. After five minutes the rereaders did better. After two days and after a week, the students who had practised recalling remembered clearly more, even though rereading felt more effective to them. The effort of pulling something out of memory is what strengthens it. The honest check is the question "can I produce it with the page closed?", not "does this look familiar?".

Applied here: cover the right-hand column of any table on this page and say the answer out loud first. Use the quizzes in Try it before reading their explanations. The trainer never shows an answer until we have tried.

3 · Space it out (distributed practice)

The same total time spread over several days beats one long session, and the best gap grows with how long we want to remember. Cepeda and colleagues' meta-analysis of hundreds of experiments found this again and again. The simplest schedule is the Leitner system. Cards live in five boxes. A card we recall moves up one box, and a card we miss goes back to box 1. Box 1 is reviewed every day, box 2 every 2 days, box 3 every 4, box 4 every 8 and box 5 every 16. Easy cards drift away; hard ones keep coming back.

Applied here: ten minutes a day with the trainer, rather than an hour on Sunday. It remembers which box each card is in, in this browser only.

5 · Make it, don't copy it (the generation effect)

Slamecka and Graf found that words people produce themselves, even from a small cue, are remembered better than words they read. Copying a command from a tutorial teaches the fingers nothing. Typing it from the goal ("add TypeScript as a dev dependency") makes us build it from the grammar.

Applied here: the trainer's command cards give a goal and check whatever we type with the command model, so npm i -D typescript and npm install --save-dev typescript both count, because npm reads them identically. Its class cards give a description and check our class against the Tailwind model.

6 · Mix the kinds (interleaving)

Practising one kind of thing at a time (all the spacing classes, then all the colour classes) feels smooth. Mixing them teaches us to tell them apart, which is the skill we need when facing a blank className. Kornell and Bjork found that interleaved examples taught categories better, even though learners believed the blocked order worked better.

Applied here: the trainer shuffles terms, commands and classes into one queue.

9 · Explain it to someone (or to a rubber duck)

Explaining forces retrieval and shows the gaps immediately: the sentence we cannot finish is the thing we did not understand. After each study session, explain one frame of this page out loud in plain words, without looking, as if to a friend who has never coded. Where we get stuck, reread only that paragraph, then try again.

Show how npm reads npm i -gD @tailwindcss/vite@latest/daisyui@latest: the command it runs, the settings it sets, and how it reads the package argument (name, scope, spec and spec type). Then fix the command so it does what the author meant.

nopt sees -gD. It is not a known option or shorthand, but every letter is a one-letter shorthand, so it expands to --global --save-dev: global = true, save-dev = true. The plain words left are i and the package argument, and deref("i") gives install.

npm-package-arg finds the first @ after position 0. The name is @tailwindcss/vite (scope @tailwindcss) and the spec is everything after that @: latest/daisyui@latest. The spec contains a slash, so it is a directory spec: npm would look for a local folder called latest/daisyui@latest. Also, -g installs for the whole computer, so -D does nothing useful.

Fix: npm install @tailwindcss/vite@latest daisyui@latest (a space between the two specs, and no -g), or -D without -g to record them as dev dependencies.

Marking: 1 for the -gD expansion, 1 for install, 2 for the name, scope and directory spec with the reason, 1 for -g making -D pointless, 1 for the fix.

A student runs npm create vite@latest app --template react-ts and gets the wrong template. Using npm's code, explain why, and why npm create vite@latest app -- --template react-ts works.

create is an alias of init. init turns vite@latest into the package create-vite@latest (the line req.name.replace(/^(@[^/]+\/)?/, '$1create-')) and runs it through npm exec with the remaining arguments.

Before that, nopt parses npm's own options. --template is not an npm option, and nopt treats an unknown option without = as a switch (typeof argType === 'undefined' && !hadEq), so it sets npm's template = true and leaves react-ts as an ordinary argument. create-vite receives app react-ts and never sees --template.

With --, nopt stops parsing (if (arg.match(/^-{2,}$/))) and pushes every later word into the plain arguments unchanged, so create-vite receives app --template react-ts.

Marking: 1 for create → init → create-vite, 2 for the unknown option becoming npm's setting and react-ts a stray argument, 2 for the -- rule.

Trace what happens from typing npm run dev to the browser running our App component. Name the program or file that does each step, and say which steps run in Node and which in the browser.

1. The shell starts npm, which is node running npm-cli.js. nopt and deref turn run into run-script. (Node)

2. run-script reads "dev": "vite" from package.json, set-path.js puts node_modules/.bin first on PATH, and the shell finds vite, a link to vite/bin/vite.js. (Node)

3. Vite reads vite.config.ts, loads the react() and tailwindcss() plugins and listens on localhost:5173. (Node)

4. The browser requests / and /src/main.tsx. For each file, loadAndTransform loads it and the plugin container calls every plugin's transform hook: types are removed, JSX becomes jsxDEV(…) calls, imports become URLs, and Tailwind writes CSS for the classes it found. (Node)

5. V8 in the browser runs the modules, createRoot(…).render(<App />) schedules a render, React calls App and its children and commits DOM nodes, and Blink styles, lays out and paints them. (Browser)

Marking: 1 for npm as a Node program, 1 for the PATH step, 1 for Vite and plugins, 2 for transform per request, 1 for the browser side.

Compare a library and a framework using inversion of control, place React and Next.js, and contrast "hook" in Vite with "hook" in React.

With a library, our code holds control and calls it (react-toastify's toast()). With a framework, it holds control and calls our code at points it defines (Next.js calls the function exported from app/about/page.tsx when /about is visited). That reversal is inversion of control.

React is in between: we call render, then React calls our components. It is called a library because it covers only the UI. Next.js decides routing, data loading and building, so it is a framework.

A Vite hook is a named moment (transform) at which the host calls a plugin's callback. A React hook is a function we call (useState) to give a component state stored on its fiber.

Marking: 1 for inversion of control, 1 for React, 1 for Next.js, 1 for the hook contrast.

Design a two-week review plan for learning this vocabulary, and justify each choice with evidence from learning research.

Short daily sessions instead of one long one, because distributed practice beats massed practice for the same total time (Cepeda et al. 2006). Each session starts with recall from memory (cards, covered tables, explaining aloud), not rereading, because retrieval practice beats restudy after days (Roediger and Karpicke 2006) and rereading is rated low utility (Dunlosky et al. 2013).

A Leitner schedule (boxes reviewed after 0, 2, 4, 8, 16 days; a miss goes back to box 1) makes the gaps grow with each success, matching the flattening forgetting curve. Mix terms, commands and classes in one queue (interleaving, Kornell and Bjork 2008). Make commands and class lists from goals rather than copying them (the generation effect, Slamecka and Graf 1978). Learn chunks (the five Tailwind rules, the command grammar) instead of lists (Miller 1956). Add a card for every lookup made during the assignment.

Marking: 1 each for spacing, retrieval, a growing schedule, one more technique (interleaving, generation or chunking), and correct justification throughout.
