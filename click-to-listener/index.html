From a click to our listener

The previous page turned HTML into pixels. Now someone clicks those pixels. We follow one press of a mouse button from the USB report and the Linux kernel, through Chrome's browser process, the renderer's compositor and main threads, the hit test that decides which element was under the pointer, and the DOM's capture-target-bubble dispatch, into our addEventListener callback, and then into the microtasks that run right after it.

The 60-second versionread this first, or come back to it after the deep dive
  1. The mouse sends a few bytes; the kernel turns the button bit into a 24-byte input_event (EV_KEY, BTN_LEFT, value 1). The window system passes it to Chrome's browser process, which picks the renderer for that spot and sends it a WebMouseEvent over Mojo, then waits for an acknowledgement.
  2. In the renderer, the compositor thread receives it first. A press or release is queued for the main thread at once; mouse moves wait to be batched with the next frame.
  3. On the main thread, hit testing walks the painting order backwards and stops at the first box under the pointer that accepts pointer events. One press gives pointerdown and mousedown; one release gives pointerup, mouseup and click, which goes to the nearest element that contains both the pressed and the released element.
  4. Dispatch builds the path once, runs capture listeners from window down, then the target, then bubble listeners back up. Each listener is called from C++ with no script on the stack, so microtasks run after every listener of a real click, but only at the end for btn.click() from script. Both are real Chrome logs below.
The hit-test lab lets us click a stage of boxes and compares the model with this browser. The dispatch lab runs any set of listeners, and its "by user" programs can be clicked for real. The trace shows the whole trip with real timings.
Frame 0 · the root

A button closes a circuit, and the kernel writes 24 bytes

A USB mouse in boot protocol sends a short report every time something changes. Byte 0 holds the buttons, one bit each; bytes 1 and 2 are the X and Y movement. The kernel's driver gets the report in an interrupt handler and turns each bit into a call to input_report_key. Then input_sync marks the end of one consistent report.

The evdev handler copies each of those values into a struct input_event in a per-reader ring buffer and wakes anyone reading /dev/input/eventN. On desktop Linux the reader is the window system (a Wayland compositor through libinput, or the X server), which sends Chrome a pointer-button message for its window. On ChromeOS, Chrome reads evdev itself; that is the EventConverterEvdevImpl code below, the same input_event structs going into Chrome's ui::Event system.

Nothing at this layer knows about pages or elements. It knows a button changed state at a time, and where the cursor is in screen coordinates. Everything after this is Chrome deciding which part of which page that position means.

Frame 1 · the browser process

Route it to the right renderer, send it, and wait for the answer

The window system's event reaches Chrome's browser process as a ui::MouseEvent on the window (Aura on Linux and Windows). RenderWidgetHostViewEventHandler::OnMouseEvent converts it to a blink::WebMouseEvent and asks the input event router where it should go. With site isolation a page can contain iframes from other sites, each drawn by a different renderer process, so the router first hit-tests surfaces: the regions each renderer's frames cover, as reported to the GPU process (Viz). With only one renderer on screen it skips that work, as the code shows.

Then RenderWidgetHostImpl::ForwardMouseEvent hands it to the input router, which sends it over Mojo with WidgetInputHandler::DispatchEvent. A press is blocking: the browser keeps it in flight until the renderer replies with whether a listener consumed it. That reply is how the browser knows, for example, whether to start a drag or show a context menu.

In our trace, the browser's ForwardMouseEvent and the Mojo send take well under a tenth of a millisecond, and the renderer's compositor thread picks the message up a few tenths of a millisecond later. The answer comes back as InputRouterImpl::MouseEventHandled after the main thread has run every listener: the browser really does wait for our JavaScript.

Frame 2 · the renderer

The compositor thread sees it first, and a press does not wait for a frame

Mojo delivers DispatchEvent on the renderer's compositor thread, not the main thread. That thread can handle some input alone: it can scroll a layer while the main thread is busy, unless a non-passive wheel or touch listener might cancel the scroll. A mouse press is not something it can handle, so MainThreadEventQueue queues it for CrRendererMain.

The queue treats event types differently. Mouse moves, wheel and touch moves are rAF-aligned: they are held and coalesced until the next frame begins, so a mouse that reports 1,000 times a second does not run our mousemove listener 1,000 times. A press or release is not in that list, so it is posted to the main thread right away.

This is the same main thread as the event-loop page. The input arrives as a task on CrRendererMain. If a long task is running, our click waits behind it, and the browser's acknowledgement waits too. That waiting is part of what the INP (Interaction to Next Paint) metric measures.

Frame 3 · hit testing

Which element is under the pointer? Walk the painting order backwards

EventHandler::HandleMousePressEvent asks for the target with GetMouseEventTarget, which ends in LayoutView::HitTest. The question "what is under this point?" must give the answer we see, so hit testing follows the same order as painting, in reverse: whatever was painted last is on top and is tested first.

PaintLayer::HitTestLayer does this per stacking context: first the children with positive z-index (highest first), then the normal-flow and z-index: 0/auto children, then the layer's own foreground, then negative z-index children, then its own background. A box is skipped when the point is outside it, when an ancestor's overflow clips it there, or when it has pointer-events: none or visibility: hidden. Both of those are inherited, and a descendant can set them back.

In the real trace, the press's HitTest event reports nodeName: #text: the pointer was over the letters of "Save". Events are not fired at text nodes, so Blink uses the nearest element, the <button>. Hit testing also updates :hover and :active, which is why it runs even when no listener exists.

    Frame 4 · which events

    One press gives two events; one release gives three

    For a press, Blink fires a pointerdown (Pointer Events) and then the compatibility mousedown, both at the hit element. If the element can take focus, focus moves next (focus, focusin). For a release it fires pointerup, mouseup, and then possibly a click.

    The click is not simply "the element under the release". MouseEventManager::DispatchMouseClickIfNeeded takes the element that got the mousedown and the element under the mouseup and sends the click to their common ancestor. We captured that: press on #a, drag to #b, release, and the click landed on #card, which contains both. That is why dragging off a button before releasing does not click it.

    Frame 5 · event dispatch

    Capture down, target, bubble up: EventDispatcher::Dispatch

    Dispatch starts by building the event path: the target, each ancestor, the document and the window. It is fixed now; moving the target to another place during dispatch does not change who is visited. Then DispatchEventAtCapturing walks the path from the window down and runs capture listeners; at the target it runs only the target's capture listeners. DispatchEventAtBubbling walks back up: the target's other listeners first, then, if the event bubbles, each ancestor's non-capture listeners.

    At each target, FireEventListeners takes a snapshot of that target's listener list. A listener added now does not run in this pass. A listener removed now is skipped, because it is marked removed. A once listener is removed just before it runs. stopPropagation() lets the rest of the current target's listeners run; stopImmediatePropagation() stops at once. A passive listener's preventDefault() is ignored.

    At the target, capture listeners run before the others whatever order we registered them in. Chrome changed this in version 89; before that, listeners on the target ran in registration order. The comment "To match Mozilla, the AT_TARGET phase fires both…" in FireEventListeners still describes the old behaviour. The "Capture runs first at the target" preset below shows the current order, and the check confirms it against Chrome 141.

        Frame 6 · our listener

        Into V8, and why microtasks run between the listeners of a real click

        A listener is called through JSBasedEventListener::Invoke, which, through the generated callback bindings, ends in V8ScriptRunner::CallFunction. That function opens a V8RunMicrotasksScope around the call. When the scope closes, V8 performs a microtask checkpoint, but only if no other script is still running underneath: ShouldPerformCheckpoint requires the scope depth to be back at zero.

        For a real click, the listener was called from C++ input handling with an empty JavaScript stack, so the depth is zero and the microtasks queued by that listener run before the next listener. For btn.click() our own script is still on the stack, the depth stays above zero, and all the microtasks wait until that script finishes. The HTML standard says the same thing in "clean up after running script".

        The capture script hit a real bug in its own first version, and it teaches the same lesson. Its microtasks read event.currentTarget. In the real click they ran during dispatch and saw the right element; after btn.click() they ran after dispatch had finished, when currentTarget is already null, and threw. Code that works for a real click can break for a scripted one.

        Exam-style questions, with model answers

        Five questions in the style of a web systems or operating systems exam. Write our answer first, then open the model answer and mark ourselves honestly. Answers that list listener orders were produced by the dispatch model and checked with the lab's real-browser check.

        Self-marks stay on this page only; refreshing clears them.
        The tree is <div id=card><div id=row><button id=btn></button></div></div>. Listeners, in order: L1 card capture; L2 btn, which calls stopPropagation(); L3 btn; L4 row; L5 card. The user clicks the button. List what runs, with each phase, and explain why L3 runs but L4 does not.
        L1 capture card
L2 target btn      (stopPropagation)
L3 target btn

        The capture pass walks window → document → html → body → card → row → btn and runs card's capture listener (L1). At the target, the bubbling pass runs btn's non-capture listeners in order. stopPropagation() in L2 sets a flag that is checked after the current target's listeners finish, so L3 still runs. The loop in DispatchEventAtBubbling then returns, so row (L4) and card (L5) never run. With stopImmediatePropagation(), L3 would not run either.

        Marking: 2 for the order, 1 for the phases, 2 for "the flag is checked between targets", 1 for contrasting stopImmediatePropagation.

        Explain why, for a real click, a microtask queued in the first listener runs before the second listener, but for btn.click() called from a script it runs after both. Name the mechanism in Blink and V8.

        Each listener is called through V8ScriptRunner::CallFunction, which opens a V8RunMicrotasksScope. When a scope closes, V8 performs a checkpoint only if ShouldPerformCheckpoint is true, which requires the microtask scope depth to be zero (no script still running). A real click is dispatched from C++ input handling, so after each listener the depth is zero and the queued microtasks run immediately. With btn.click(), our script's own scope is still open, so the depth is at least one during the whole dispatch; the checkpoint happens when our script's scope closes, after click() returns. The HTML standard's "clean up after running script" states the same rule.

        Marking: 1 for the scope, 2 for the depth-zero condition, 1 for each case.

        A stage contains: a at (20, 20) size 200 × 160 with z-index: 1; inside it a1 at (20, 20) relative to a, size 140 × 80, z-index: 100; and b at (120, 60) size 200 × 160 with z-index: 2. Which element does a click at (150, 90) hit? What changes if a has no z-index?

        The point (150, 90) is inside a (20–220, 20–180), inside a1 (40–180, 40–120) and inside b (120–320, 60–220). With z-index: 1, a is a stacking context, so a1's 100 only orders it inside a. The stage paints a's whole group at level 1, then b at level 2. Backwards: b is first and contains the point, so it is the hit.

        Without a z-index, a does not form a stacking context, so a1 takes part in the stage's order at level 100, above b. The hit becomes a1. (Both are the lab's presets; the model and elementFromPoint agree.)

        Marking: 1 for the containment check, 2 for the stacking-context argument, 2 for the second case.

        Write a short note on why Chrome sends mouse presses to the main thread at once but delays mouse moves, and what that means for a mousemove listener.

        MainThreadEventQueue::IsRafAlignedEvent returns true for mouse moves, wheel and touch moves. Those events are held until the next frame and coalesced, so a 1,000 Hz mouse produces about one mousemove dispatch per frame (a pointermove event's getCoalescedEvents() returns the reports that were merged). Presses and releases are discrete and their order matters, so they are posted to the main thread immediately. A mousemove listener therefore runs about once per frame, just before rendering, and should not expect one call per hardware report.

        Marking: 1 for naming the queue, 1 for coalescing, 1 for why presses are not delayed, 1 for the consequence.

        Trace a left mouse press from the USB report to the first JavaScript listener, naming one function or structure at each layer: kernel, browser process, renderer compositor thread, renderer main thread before dispatch, and dispatch.

        Kernel: usb_mouse_irq reads bit 0 of byte 0 and calls input_report_key(dev, BTN_LEFT, 1); evdev stores a struct input_event (EV_KEY, BTN_LEFT, 1) followed by SYN_REPORT. Browser process: the window system's event becomes a ui::MouseEvent; RenderWidgetHostImpl::ForwardMouseEvent sends a WebMouseEvent through InputRouterImpl as a blocking Mojo DispatchEvent. Compositor thread: WidgetInputHandlerImpl::DispatchEvent, then MainThreadEventQueue queues it for the main thread (not rAF-aligned). Main thread: WidgetBaseInputHandler::HandleInputEvent → EventHandler::HandleMousePressEvent → hit test through LayoutView::HitTest. Dispatch: EventDispatcher::Dispatch fires pointerdown; the first capture listener on the path is called by FireEventListeners.

        Marking: 1 per layer with a correct name.
