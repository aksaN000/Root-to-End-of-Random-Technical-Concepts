From the power button to .then()

We already know processes, threads, syscalls and scheduling. This page uses exactly those ideas to follow one fetch().then() through the actual code that runs it: the process that hosts our React tab, the C++ thread that runs our JavaScript, the exact line that starts its event loop, the system call it sleeps in, and the V8 builtin that queues our callback.

The 60-second versionread this first, or come back to it after the deep dive
  1. Our JavaScript runs on one OS thread, CrRendererMain, in the tab's renderer process. One piece of code runs at a time, to completion.
  2. That thread loops forever: run one task, then run every microtask, then maybe render, then sleep in the kernel until something wakes it.
  3. Timers, network replies and clicks arrive as tasks. Promise callbacks and the code after await run as microtasks.
  4. So all pending microtasks run before the next task: log(1); setTimeout(log 2); Promise.then(log 3); log(4) prints 1 4 3 2.
The rest of the page proves each sentence from source: the line that starts the loop (RendererMain), the for (;;), the kernel wait, and V8's microtask queue. Or jump straight to the playground.
Frame 0 · the root

The OS gives Chrome a process

Everything starts the way any program does. When we launch Chrome, the kernel creates a process: a fresh virtual address space, a handle table, and one thread whose instruction pointer starts at the executable's entry point. On Windows that entry point is wWinMain in chrome.exe. Nothing about events, promises or JavaScript exists at this point.

Chrome then becomes many processes. It does this with the same primitives we studied: CreateProcess on Windows, fork() plus execvp() on Linux. The browser process launches itself again, as chrome.exe --type=renderer …, and the command-line flag decides which main the child runs.

On Linux, renderers are usually forked from a pre-warmed zygote process rather than through this exact path, and on Windows the sandbox broker creates the renderer under a restricted token. The idea is identical: the browser process asks the kernel for a new process, then that child picks its role from --type=.

Frame 1 · the layout

Chrome's processes, and which thread is our tab

Each box is a separate OS process with its own address space. Inside, each item is an OS thread. The thread names are the strings Chrome passes to SetName or base::Thread. Two of them appear verbatim in the excerpts on this page: CrRendererMain and Chrome_ChildIOThread.

So "JavaScript is single-threaded" means precisely this: our code only ever runs on CrRendererMain, which is one OS thread in one renderer process. The process itself has many threads. Our fetch is performed by a different process entirely. Web Workers get their own threads, each with its own event loop.

Frame 2 · entry points

From wWinMain to RendererMain

The renderer child starts in the same executable as the browser. The path down to the renderer-specific code is a chain of ordinary function calls: the Windows entry point loads chrome.dll, which calls ContentMain, which reads --type and dispatches through a table of function pointers.

That table is the whole answer to "how does one executable become a renderer": process_type == "renderer" means call RendererMain. The browser process, which has no --type, takes a different branch into BrowserMain instead.

Frame 3 · the answer

The line that starts our tab's event loop

This is the main thread of the renderer process. Read it top to bottom and we watch the event loop get assembled: name the thread, initialize Blink, build a scheduler around a message pump, create the RenderThreadImpl (which also starts the IO thread), engage the sandbox, and finally call run_loop.Run().

That call does not return until the tab's process shuts down. Every task this renderer ever runs, including parsing our HTML, executing main.jsx, and every React render, happens inside it, deeper on this thread's C++ stack.

Note MessagePumpType::DEFAULT. The renderer main thread's pump does not watch sockets or pipes itself. It sleeps on a plain event and is woken by other threads. We will see why that matters in the IO thread section.

Frame 4 · the loop itself

Inside run_loop.Run()

RunLoop::Run hands off to the thread's controller, which calls pump_->Run(this). Here is the pump: an actual for (;;). Strip out the metrics and the busy-wait heuristic and it is four lines: do work, if there's more do it again, otherwise do idle work, otherwise sleep until signaled or until the next delayed task is due.

delegate->DoWork() is where a task, in the HTML-spec sense, actually runs. The scheduler chooses the next task from several prioritized queues (input, loading, timers, and others), runs it, then calls DidRunTask. The comment in the source says that last call can process microtasks. That is the microtask checkpoint we traced earlier, happening right after each task.

Two details worth keeping. First, DoWork runs tasks in batches of up to 8 ms before going back to the pump. Second, task_execution_allowed is set to false while a task runs, which is why one task can never start inside another. A while(true){} in a click handler never returns from RunTask, so the for (;;) above never comes back around to anything else: no other task, no paint, no input.

Frame 5 · the bottom of the stack while idle

How the loop sleeps without burning CPU

When there is no work, the pump calls event_.TimedWait(remaining_delay). On Windows that is a kernel event object and WaitForSingleObject, so the scheduler takes the thread off the CPU. On Linux and macOS, Chrome builds the same thing from a mutex and a condition variable, the textbook construction.

Waking it is the mirror image: any thread that posts a task to the main thread ends up calling MessagePumpDefault::ScheduleWork(), which calls event_.Signal(), which on Windows is SetEvent.

Frame 6 · the other thread

Who signals that event: Chrome_ChildIOThread

The main thread's pump is DEFAULT; the IO thread's pump is IO. An IO pump blocks in the kernel's readiness mechanism, epoll on Linux and an IO completion port on Windows, waiting on the pipes that connect this renderer to the browser and network processes. When a message arrives, the IO thread wakes, decodes the Mojo message, and posts a task to the main thread. Posting is what calls ScheduleWork and signals the event from the previous section.

The complete wake chain for our fetch reply

NIC → kernel

The network card raises an interrupt. The kernel's TCP stack reassembles the bytes and marks a socket readable.

network process

Its thread wakes from epoll or IOCP, reads the socket, decrypts TLS, parses HTTP, and sends the response over a Mojo pipe to our renderer.

Chrome_ChildIOThread

Wakes from its own epoll or IOCP wait on that pipe, decodes the Mojo message, and posts a task to the main thread's loading queue.

PostTask

Enqueues the task and calls ScheduleWork(), then event_.Signal(), then SetEvent or a condition-variable broadcast.

CrRendererMain

Returns from WaitForSingleObject, goes back around for (;;), and DoWork picks the task. The task resolves p1, which queues our .then callback as a microtask.

Frame 7 · inside V8

What .then(), resolving, and the microtask queue actually are

V8 implements Promise.prototype.then as a builtin written in Torque, V8's own language for builtins, which compiles to machine code. It allocates the result promise and calls PerformPromiseThenImpl.

This is the branch we watched in the simulator. If the promise is still pending, .then stores a PromiseReaction on it, and nothing is queued. That is the "stapling" step. If the promise has already settled, it skips straight to EnqueueMicrotask.

When the network task later resolves p1, FulfillPromise flips the state and hands the stored reactions to TriggerPromiseReactions. That morphs each reaction object in place into a job task and pushes it onto the microtask queue.

The microtask queue itself is a C++ ring buffer whose capacity doubles when full. A checkpoint drains it completely, including any microtasks queued while draining, which is why a chain of resolved promises all run back to back with no paint in between.

Ownership, confirmed by the code: V8 owns the microtask queue; Blink decides when to drain it (EventLoop::PerformMicrotaskCheckpoint); Chromium's base library owns the task loop and the sleep. The V8 comment above notes that checkpoints happen whenever script or microtask scopes exit, not only once per task.

Frame 9 · our code

Where our React app sits in all of this

With npm run dev, Vite serves an index.html containing <script type="module" src="/src/main.jsx">. Module scripts are deferred, so after parsing finishes, one task on CrRendererMain executes main.jsx. Inside that task, createRoot(...).render(<App />) runs. React then schedules its work, and effects run in later turns of the same loop.

A typical data-loading component maps directly onto the trace:

The setUser call inside the callback runs during a microtask checkpoint. React batches the update and re-renders, and the new DOM reaches the screen at the next render opportunity of the loop, which is phase 3 in the simulator. The ignore flag exists because the component can unmount while p1 is still pending: the promise lives on the heap regardless, and its callback would still run later.

Frame 10 · contrast

Node.js: same V8, a different loop

Node embeds the same V8, so .then and the microtask queue are the identical Torque code above. The task loop is different: libuv's uv_run, with named phases. Node runs our entire script first and only then spins the loop, and the loop exits by itself once uv_loop_alive reports nothing left to wait for. That is why a Node script ends but a tab does not.

A button's click handler runs a loop that takes 3 seconds. Using the renderer's run loop, explain why the page cannot repaint or handle another click during those 3 seconds. Name one thing that may still work.

The click handler is one task. DoWork calls RunTask, and it does not return until our handler returns. The for (;;) in MessagePumpDefault::Run only picks the next task, runs the microtask checkpoint, or reaches a rendering opportunity between tasks, so for 3 seconds nothing else on CrRendererMain can run: no input tasks, no timers, no paint.

What may still work: scrolling of already painted content, because the compositor thread handles it off the main thread (unless a non-passive wheel or touch listener forces it to wait for the main thread). Input still reaches the renderer through Chrome_ChildIOThread; it simply queues until the task ends.

Marking: 2 for "one task runs to completion, the loop cannot interleave", 1 for naming where (RunTask / DoWork / the pump), 1 for the compositor.

Distinguish a task from a microtask. Give two sources of each and state exactly when the microtask checkpoint runs.

A task is a unit the event loop picks one at a time from its task queues. A microtask is a job in V8's microtask queue; the queue is drained completely at each checkpoint, including microtasks queued during the drain.

Task sources: timer callbacks (setTimeout), network responses, user input events, postMessage. Microtask sources: promise reactions (.then, .catch), the continuation after await, queueMicrotask, MutationObserver callbacks.

The checkpoint runs after each task finishes (Chromium reaches it from DidRunTask), and also whenever the JavaScript stack empties after a callback, for example between two event listeners of one click.

Marking: 1 for the definitions, 1 for task sources, 1 for microtask sources, 1 for the timing.

Rewrite this function using only .then (no async/await). Then describe what happens to load's stack frame at the await, and what wakes it up again.
async function load() {
  console.log("start");
  const r = await fetch("/a");
  console.log("got", r.status);
  return r.status;
}
function load() {
  console.log("start");
  return fetch("/a").then(r => {
    console.log("got", r.status);
    return r.status;
  });
}

At await, load returns its promise to the caller and its frame is popped off the call stack. V8 keeps the rest of the function in a suspended generator-like object and stores a PromiseReaction on the fetch promise; nothing is queued while the request is in flight.

The network process receives the response, sends it over Mojo to the renderer's IO thread, which posts a task to CrRendererMain. That task fulfills the fetch promise, TriggerPromiseReactions queues our continuation as a microtask, and at the checkpoint after that task load resumes with r.

Marking: 2 for a correct rewrite that returns the status, 2 for "frame popped, reaction stored, nothing queued", 2 for the wake chain (task fulfills promise, microtask resumes).

Why does a Node.js script with one pending setTimeout stay alive and exit right after the timer fires, while a browser tab never exits on its own?

Node runs our script first and then calls uv_run in SpinEventLoop. uv_run loops only while uv_loop_alive reports active handles or requests. The pending timer is an active handle, so the loop sleeps in epoll_wait until it is due, runs it, finds nothing left alive, returns, and the process exits.

A renderer's loop is started by run_loop.Run() in RendererMain before any page script exists, and it only returns when the browser process tells the renderer to quit. An empty queue just means the thread sleeps waiting for the next task.

Marking: 2 for Node (uv_run, loop alive), 2 for the browser (run_loop.Run until told to quit).
